# Impeccable

## Design Context

### Users
Minecraft server developers — largely Skript users considering a switch, plus the
language's own author. They read docs at night, in the dark, next to a terminal and
a Minecraft client. The job: learn fast by READING CODE, map what they already know
(Skript) onto SwoftLang function-by-function, and look up exact syntax while writing
scripts. Code is the content; prose is connective tissue.

### Brand Personality
Engineered, sharp, alive. A compiler that catches your bugs before the server boots —
confident and a little playful, never corporate. Not "monospace = technical" lazy;
precision shown through typography discipline and honest, dense information design.

### Aesthetic Direction
Dark-first (audience context: evening, terminals, game client), light theme supported
but designed second. Emerald stays as the single brand accent hue (tint neutrals
toward it, OKLCH), used at 10% visual weight — surfaces are calm near-black greens,
not neon-on-black. Explicit ANTI-references: default VitePress theme (the current
look — owner's verdict "horrific"), doc-site sameness (fat sidebar, narrow centered
prose column, boxed code), 2024-AI dark-glow aesthetics.
Explicitly wanted by the owner: code blocks FULL WIDTH; comparison views that scroll
together and show function→function mappings; integrated sections, not fragmented
stub pages; a guide broken into numbered steps; no implementation trivia in
user-facing guides.

### Design Principles
1. Code owns the width. Prose is capped (~70ch); code containers escape the measure
   and run wide. Never shrink code to preserve a sidebar.
2. Mapping over prose: teach by aligned correspondence (Skript row ↔ SwoftLang row),
   structurally synced (shared grid rows scroll as one), cross-highlighted on hover.
3. Progressive steps: the guide is a numbered course with visible progression, one
   concept per step, ending in something runnable.
4. Compiler as character: real diagnostics, byte-exact, are a feature of the docs —
   errors are shown, styled, and celebrated.
5. Navigation must always answer "where am I / where can I go" WITHOUT hunting:
   a persistent grouped left sidebar showing the full tree (Guide steps, Reference
   topics, Libraries, Examples), current page highlighted, section collapsible.
   The sidebar coexists with rule 1 — code still breaks out wider than the prose
   column (overlapping toward the right gutter), so a sidebar never shrinks code.
   No per-page minimap (it duplicated the sidebar and oriented poorly).

### Writing voice (language-reference register — NOT marketing, NOT AI)
- These are LANGUAGE DOCS. Write like the Rust Book / Elixir / Go docs: direct,
  declarative, present-tense, second person only when instructing.
- BANNED: any narration of the implementation's history — no "this used to be C++",
  "previously", "the old parser", "unlike the JNI version", "we rewrote". A reader
  learning SwoftLang does not care what it was. State what IS.
- BANNED AI tells: "Let's...", "In this section we'll...", "Now that we've...",
  "It's worth noting", "Simply", "Powerful/seamless/robust/leverage", rhetorical
  questions as section openers, restating the heading in the first sentence,
  over-hedging, and paragraph scaffolding that says nothing. Cut throat-clearing;
  lead with the fact or the code.
- Every page opens with what the construct IS and a minimal example, then the rules,
  then edge cases. Reference pages are scannable (tables, tight definitions), guide
  steps are a short arc to a runnable result. Show, don't sell.
