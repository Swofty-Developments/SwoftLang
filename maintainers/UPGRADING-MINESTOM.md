# Upgrading Minestom — maintainer runbook

This is the internal runbook for bumping the pinned Minestom version in SwoftLang.
It is grounded in the current codebase (Minestom `2026.07.12-26.2`, Java-25 bytecode,
Gradle 8.5 launcher on JDK 21). Follow it top to bottom. **Minestom is a rolling
snapshot with no semantic-version deprecation policy — it renames and reshapes public
API between snapshots without warning.** Assume every surface below is broken until
`javap` proves otherwise. Do not trust your memory of the Minestom API; verify.

All paths are relative to the repo root `/mnt/work/VSC/SwoftLang`.

---

## TL;DR checklist (copy-pasteable, in order)

1. **Bump the coordinate** in `java/build.gradle.kts` (`net.minestom:minestom:<new>`).
   Check the transitively-forced versions of `adventure-*`, `it.unimi.dsi:fastutil`,
   and `dev.hollowcube:polar` — bump those pins in the same file if Minestom moved them.
2. **Check the bytecode level.** If the new snapshot ships a different Java bytecode
   version, adjust the toolchain (`java/build.gradle.kts` `languageVersion`, the two
   `execHarness`/launcher blocks, `gradle.properties`, `demo/run.sh`, and
   `.github/workflows/release.yml`). See "The JDK/Gradle toolchain quirk".
3. **Compile:** `taskset -c 0-11,14-31 nix-shell -p jdk21 --run './gradlew :java:compileJava --console=plain'`.
4. **Fix compile breaks surface by surface** using the "API surface map" table below.
   `javap` each class before you change its call site.
5. **Regenerate the data catalogs** (`events.json`, `entity-api.json`, `events_data.ml`,
   `packets.json`) from the new jar with `GenMinestomCatalogs`. Mandatory — see "Regenerating data catalogs".
   (There is currently no `block_states.json`; if a future block change needs one, add it
   to the generator rather than hand-editing.)
6. **Rebuild the OCaml compiler** (`cd compiler && dune build`) so the regenerated
   `events_data.ml` is embedded, then **regenerate every script sidecar** (`scripts/*.sw`,
   `addons/*.sw`, `demo/scripts/*.sw`) — see "Regenerating script sidecars".
7. **Run the full verification gauntlet** (harness modes + `--check-props` + `dune test` +
   `validate-snippets.py`). All green.
8. **Boot the demo** against a real client (`demo/run.sh`) and confirm join + a command.
9. **javap-verify every changed signature** one more time against the new jar.
10. **Update the version strings** everywhere (see "Version-pin locations" — there are
    ~10 places, several are comments/`minestomCommit` fields that drift silently).

## The JDK/Gradle toolchain quirk (read before touching toolchains)

Minestom `26.2` ships **Java-25 bytecode** and its Gradle module metadata declares
`org.gradle.jvm.version=25`, so the *consumer* toolchain must be 25 for variant
selection to succeed. But the Gradle wrapper (`gradle/wrapper/gradle-wrapper.properties`)
pins **Gradle 8.5, which runs on JDK 21**. The resolution:

- **Gradle launcher runs on JDK 21**; **JDK 25 is used only as the compile/run toolchain.**
- `java/build.gradle.kts` sets `java { toolchain { languageVersion = 25 } }` and the
  `execHarness` task pins a JDK-25 `javaLauncher` (bytecode is Java-25, so the harness
  JVM must be 25 too — a JDK-21 launcher throws `UnsupportedClassVersionError`).
- JDK 25 is discovered via **foojay auto-provisioning** (the
  `org.gradle.toolchains.foojay-resolver-convention` plugin in `settings.gradle.kts`),
  or a locally installed JDK 25, or an explicit pin via
  `org.gradle.java.installations.paths` in `~/.gradle/gradle.properties` (documented in
  the repo `gradle.properties`).
- **CI** (`.github/workflows/release.yml`) installs both JDK 21 and 25 and wires them
  explicitly: `JAVA_HOME="$JAVA_HOME_21_X64" ./gradlew :java:jar -Dorg.gradle.java.installations.paths="$JAVA_HOME_25_X64"`.
- **Local demo run** (`demo/run.sh`) resolves JDK 25 from nix (`nix-shell -p jdk25`) for
  the runtime, and JDK 21 for the build.

**If the new snapshot changes bytecode level** (e.g. Java 26): update `languageVersion`
in `java/build.gradle.kts` (the `java{}` block **and** the `execHarness` launcher block),
the comments in `gradle.properties` and `demo/run.sh`, the `nix-shell -p jdkNN` in
`demo/run.sh`, and the `java-version:` list + `JAVA_HOME_25_X64` reference in
`release.yml`. If Minestom requires a newer Gradle, also bump
`gradle/wrapper/gradle-wrapper.properties`.

## Regenerating data catalogs (mandatory)

The compiler ships four files generated **from the Minestom jar by reflection** —
`compiler/data/GenMinestomCatalogs.java`:

- `compiler/data/events.json` — 101 engine events with `className/shortName/cancellable`
  and per-property `{name, javaType, settable, accessor}`. Also embedded into the server
  jar as `/events.json` (see `processResources` in `java/build.gradle.kts`).
- `compiler/data/events_data.ml` — the OCaml fragment of the same catalog, **copied into
  the compiler library at build time** (`compiler/lib/dune` has a `(rule … copy
  ../data/events_data.ml)`) so `compiler/lib/registry.ml` can typecheck event property
  access.
- `compiler/data/entity-api.json` — the `EntityType` registry + entity property surface.
- `compiler/data/packets.json` — every concrete public record under
  `net.minestom.server.network.packet.**` implementing `ClientPacket` (inbound, the ones a
  `Packet { on "..." }` block listens to) or `ServerPacket` (outbound), keyed by FQN, with
  `{simple_name, direction, fields:[{name, accessor, javaType, ty}]}`. Powers `packet.<field>`
  typing + LSP completion inside `Packet` blocks. `ty` uses the SAME `javaType->ty` table as
  the events catalog — `GenMinestomCatalogs.tyOfJavaType` is a hand-kept mirror of
  `compiler/lib/registry.ml` `ty_of_java_type`; **when you touch one, update the other.**

**These MUST be regenerated on every upgrade** — event class names, getter/accessor
signatures, cancellability, and registry entries drift between snapshots (e.g. the entity
event count grew across `26.2`). Stale catalogs mean the compiler accepts scripts the
runtime can't execute, or rejects valid ones.

Regenerate (deterministic output — sorted, no timestamps, so diffs are clean):

```sh
# CP = runtime classpath of the :java module (NEW pinned jar + transitive deps).
CP=$(nix-shell -p jdk21 --run "./gradlew -q :java:showDependencies" | tr '\n' ':')
JAR=$(echo "$CP" | tr ':' '\n' | grep 'minestom.*\.jar')   # the pinned jar itself
nix-shell -p jdk25 --run "
  javac -d /tmp/gencat compiler/data/GenMinestomCatalogs.java &&
  java -cp /tmp/gencat:$CP GenMinestomCatalogs $JAR /mnt/work/VSC/SwoftLang/compiler/data
"
```

Update `GenMinestomCatalogs.COMMIT` to the new version first. The tool prints a sanity
summary (`events=`, `cancellable=`, `fishing=`, `loadErrors=`, `packets=` with its
`client=`/`server=` split, and `packetLoadErrors=`) — **both `loadErrors` and
`packetLoadErrors` must be empty**; a non-empty list means a class in the scanned package tree failed to load
(usually a moved/removed dependency) and the catalog is incomplete. Diff the JSON to see
exactly which events/properties changed and cross-check those against the API surface map.

> **`block_states.json`:** none exists today. If a future Minestom upgrade requires
> validating block-state property names/values in the compiler, add a generator pass to
> `GenMinestomCatalogs.java` (dump `Block` registry + property keys) rather than
> hand-writing it — same determinism/regeneration discipline applies.

### Regenerating script sidecars

Every `.sw` script has a checked-in `<name>.sw.json` **sidecar** (the compiled JSON AST)
used as a runtime fallback when `swoftc` isn't on `PATH`. After the compiler is rebuilt
with the new catalog, these can drift, so recompile them all:

```sh
cd compiler && dune build && cd ..
SWOFTC=compiler/_build/default/bin/main.exe
for f in scripts/*.sw addons/*.sw demo/scripts/*.sw; do
  "$SWOFTC" compile "$f" -o "$f.json"
done
```

Sidecars are consumed by `net.swofty.compiler.SwoftcCompiler` (falls back to
`<script>.sw.json` when no binary is found).

## Verification gauntlet (prove it green)

Run all of these; every one must pass. Pin CPU-heavy steps with `taskset -c 0-11,14-31`.

```sh
# 1. Java compiles against the new jar (main + test/harness):
taskset -c 0-11,14-31 nix-shell -p jdk21 --run './gradlew :java:compileJava :java:compileTestJava --console=plain'

# 2. Build the compiler + run its tests (includes property-table + snippet fixtures):
cd compiler && dune build && dune test && cd ..

# 3. Property-table byte-identity / cross-check: the OCaml registry
#    (compiler/lib/registry.ml → compiler/test/property-table.json) and the Java
#    PropertyRegistry must agree exactly. dune test checks the OCaml side; the Java side:
nix-shell -p jdk21 --run './gradlew :java:execHarness -PharnessArgs="--check-props"'

# 4. Harness modes — each is a self-contained pass/fail proof (see ExecHarness.main):
for m in --module-test --phase6-checks --http-test --sched-test --worlds-test \
         --phase7-smoke --phase8-checks --phase9-checks --map-test \
         --collections-test --phase10-smoke --debug-smoke --packets-check --worlds-test; do
  nix-shell -p jdk21 --run "./gradlew :java:execHarness -PharnessArgs=\"$m\""
done
# script-level modes (compile + execute every command/event block against a capturing sender):
for s in scripts/showcase.sw scripts/items.sw scripts/events.sw scripts/mobs.sw; do
  nix-shell -p jdk21 --run "./gradlew :java:execHarness -PharnessArgs=\"$s\""
done
# persistence round-trip:
nix-shell -p jdk21 --run './gradlew :java:execHarness -PharnessArgs="--persist-test scripts/persist.sw"'

# 5. Docs snippet validation (every doc fence is checked against the real compiler):
python3 docs/scripts/validate-snippets.py

# 6. Boot the demo against a real client and confirm join + a command work:
./gradlew :java:jar && ./demo/run.sh   # connect a client to localhost:25565
```

**Sidecar byte-identity check.** The `.sw.json` sidecars must equal a fresh compile of
their `.sw`. After regenerating them, `git diff --stat scripts/ addons/ demo/` should show
only intended changes; regenerate + commit them together with the catalog so the runtime
fallback never disagrees with the binary. The `--check-props` harness is the load-bearing
byte-identity gate between the OCaml and Java property tables.

**javap-verify before you trust ANY signature.** Minestom changes public API without
deprecation. When a call site compiles by luck but behaves oddly, disassemble the class
(`javap -cp "$CP" -p <fqcn>`) and read the actual signature from the new jar — never
assume the shape from an older snapshot or from memory.

## Known gotchas from the last upgrade (#51, → 26.2)

- **Auth API rework.** `MinecraftServer.init(Auth)` now takes an `Auth` record at
  construction time (was a post-init toggle). `Bootstrap.resolveAuth` maps
  `mojang → Auth.Online`, `velocity "secret" → Auth.Velocity(secret)`,
  `bungeecord → Auth.Bungee`, `offline → Auth.Offline`. **Scripts are parsed BEFORE
  `MinecraftServer.init`** so the auth kind (from the `server {}` block) is known first —
  don't reorder that in `Bootstrap`.
- **`DataComponents`** replaced the old component access; `items/ItemProperties.java` and
  `ItemRegistry.java` are the blast radius. Expect constant renames on the next bump.
- **`LightingChunk`.** `instanceContainer.setChunkSupplier(LightingChunk::new)` is
  gated on `server { lighting }` (default on); plain chunks render pitch black. Keep the
  supplier signature in sync.
- **`TeamsPacket` field regroup.** `Phase5Harness.java` documents that 26.2 regrouped the
  flat `CreateTeamAction` fields into a nested structure — nametag/tablist packet code is
  fragile here.
- **Entity event count grew.** `Phase7Smoke.java` notes the regenerated catalog carries
  more entity events than before (was 87) — always regenerate `events.json`, never
  hand-patch counts.
- **`serverProcess` accessor.** `EventRegistrar.java` notes 26.2 changed how
  `MinecraftServer` exposes the `ServerProcess` before `init` — check this accessor.
- **Profile API** (`GameProfile` / `ResolvableProfile` / `PlayerSkin`) was reworked;
  `nametags`, `ui/*`, and `skins/SkinFetcher.java` depend on it.
- **Protocol/Minecraft version string** is not a Java constant — it's implicit in the jar
  and only appears as prose in `README.md`/`docs/`. Update those by hand and confirm the
  demo's server-list ping shows the right version to a client.
